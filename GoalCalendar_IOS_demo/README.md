## 核心设计：LLM 只做语义切分，日期算术全在代码里

这是整个项目最重要的一条纪律，用结构而非纪律来保证：

```
用户："明天下午三点开会"
        │
        ▼  LLM 只输出这些
   {"intent":"add_event", "title":"开会",
    "time":{"day":"tomorrow","period":"afternoon","hour":3}}
        │
        ▼  TimeResolver 用用户的 Calendar 算出
   2026-10-19 15:00 — 2026-10-19 16:00
```

模型**永远不输出**绝对日期、不做星期推算、不做时区换算、不检查冲突。
`TimeResolver` 是代码里唯一把"明天"变成日期的地方 —— 它可以被单元测试钉死到分钟，
而模型的输出做不到这一点。

代价是提示词更长、模型要多填几个字段；换来的是排程结果可复现、可审计。

**降级策略**：模型没配、断网、返回非法 JSON、返回低置信度 `unknown`，
全部静默回落到 `RuleBasedIntentParser`。日历 App 不应该因为网络抖动而拒绝接受输入。

## 排程器怎么打分

输入只有：用户时区/可用时段、待做步骤、已有事件、最近状态。无数据库、无网络、无时钟读取 ——
`now` 是参数，所以行为可以测试到分钟。

| 因素 | 影响 |
|---|---|
| 拖延天数 | 每天 **-7 分**，压过其他所有加分（否则远期目标永远开不了工） |
| 午餐 12–13 点 | -12 |
| 21 点之后 | -18 |
| 「累」 | 上午 9–11 **+12**，20 点后 -15，短步骤 +4 |
| 「忙」 | 当天 +6，长步骤（≥60 分钟）-10 |
| 「没灵感」 | 10–16 点 **+10**，连续空闲 ≥90 分钟 +8 |
| 同目标当天已有安排 | -10（避免堆在一起） |
| 状态超过 24 小时 | 完全忽略 |

推荐理由是**代码拼出来的**，不是模型写的 —— 要让用户提交真实时间，理由必须可核对。

## 确认闸门：AI 只能提议，不能写库

```
用户说话
   │
   ▼
IntentParser / GoalBreakdownParser      只提取语义
   │
   ▼
ChatOrchestrator.handle()               产出 ProposedAction（惰性数据）
   │                                     ← 此刻日历表一行都没变
   ▼
用户点「确认」
   │
   ▼
ChatOrchestrator.commit()               这时才写库
```

规则：

- `handle()` 只允许写一件事：用户自己报告的状态（`state_logs`）。因为那就是用户的原话。
- 事件、目标、步骤的写入只能走 `commit()`。
- 提案是一次性的：界面上处理过之后 `resolved = true`，按钮消失，防止双击写入两条。
- 有测试直接断言 `handle()` 调用前后日历表为空 —— 这是回归防线，不是注释约定。

## 目标拆解怎么保证质量

模型很可能返回 20 步、重复标题、一条 600 分钟的步骤。`BreakdownValidator` 在写库前
统一清洗，规则是确定的：

| 输入问题 | 处理 |
|---|---|
| 超过 15 步 | 只保留前 15 步 |
| 少于 8 步 | 保留但给出提示（不强行凑数） |
| 少于 3 步 | 判定为拆解失败，退回通用模板 |
| 标题重复 / 为空 | 保留第一条 / 丢弃 |
| 时长 < 15 或 > 240 分钟 | 夹到边界 |
| 缺 `estimated_minutes` | 默认 45 |

`percent` 仍由数据库按 `100/N` 计算，提示词里明确禁止模型输出百分比。

**原子性**：`createGoal(goal:steps:)` 用单个事务写入目标与全部步骤。任何一步失败
（例如 `seq` 重复触发唯一约束），整个目标回滚 —— 不存在“有目标、没步骤”的中间态。

**耗时**：12 步拆解实测约 30 秒，远慢于意图解析（约 2 秒）。默认超时已从 30 秒放宽到
90 秒，否则好结果会被超时静默替换成通用模板。对话界面必须明确显示“正在拆解”状态。

## 未完成怎么处理

```
助手： 「X」原定 10月19日 15:00–16:00，完成了吗？
用户： 没完成
助手： 这次没做成，我先把它从日历上撤掉了。是临时有事，还是这一步本身有点重？
      [ 临时有事 ]  [ 太难了 ]
        │              └─ 把这一步拆成两个更小的（各半小时），并给上半部分排新时间
        └─ 保留这一步，直接给下一批空档
```

三个要点：

1. **先撤掉旧事件再谈改期。** 不撤的话同一个步骤会同时挂着一条过期事件和一条未来事件，
   之后所有查询都会看到"两次"。
2. **拆细仍然在同一个目标里**，不会分支成第二个目标。拆分后步骤总数 +1，`percent`
   会整体重算（100/N），否则进度加起来不再是 100%。
3. 拆分走事务，并且先给所有 `seq` 加 1000 再回填，否则中途会撞 `UNIQUE(goal_id, seq)`。

## 事件三色

蓝 / 红 / 黄三档，新建面板和事件详情里都能改（详情里改动立即生效）。月历圆点、日时间轴、
周视图都按各自颜色渲染。黄色取的是偏暗的金色 —— 纯黄在白底上读不出来。

## 主动排程：助手先开口

打开对话时，助手会自己发起一轮（每次启动一次，不打扰）：

1. **有逾期步骤** → 「「X」原定 10月19日 15:00–16:00，完成了吗？」→ 完成了 / 没完成
2. 没有逾期 → 找第一个**还没排期**的步骤 → 「「X」还没有排时间，最早可以放在 今天 11:00。」
3. 点「没完成」→ 立刻给出一组新的空档，选一个即写入

设计上的两个选择：

- **「没完成」不静默改期**，而是给出新时间让你一点。确认闸门是一致的 —— 写日历前先看到方案。
- 跳过已排期的步骤，但**继续往后找**。之前的实现遇到最高优先级步骤已排期就直接放弃了，
  等于助手永远不说话 —— 这是个真 bug，已修。

## 系列操作的两个入口

| 入口 | 适合 | 能力 |
|---|---|---|
| 点开一个重复事件 | 想改**具体日期时间** | 这一次 / 这次及以后 / 全部 |
| 对话 | 想批量改**钟点**，不用点 | 全部（先给提案再确认） |

既然是实例存储，作用域就是一次日期比较（`SeriesScopeFilter`），不需要例外表：

- **这一次** → 只改当前行
- **这次及以后** → `startAt >= 当前事件.startAt`
- **全部** → 整个 series

界面上把「保存时间」和「删除」都绑定到同一个范围选择器，避免"改了时间却只删了一次"这类错位。

改期用**日历增量**（天数 + 分钟）而不是绝对时间偏移，所以"+1 天"跨过夏令时之后仍然是同一个墙钟时间。

## 系列级操作：让模型定位，让代码执行

「把每周四上午 9-10 的会全部改到下午 14-15」这类请求，关键不在理解，而在**改哪几行**。

- 模型只输出结构化线索：`series_match`（weekday / hour / title）+ `series_target`（新钟点 / 时长）
- `SeriesMatcher` 用这些线索在代码里找系列，**匹配不上就返回空**，绝不猜
- `SeriesEditor` 按墙钟语义算出每一次的新时间（同一天、新钟点），而不是加固定偏移 —— 加偏移会在夏令时切换时漂移
- 提案先给用户看，确认后才批量更新（单事务，不会改一半）

匹配是保守的：标题、星期、小时三项都对上才认；只有单一线索时宁可要求用户说清楚。

`hour` 在这一层用 **24 小时制**（要跟库里的真实时间比对），和意图解析里 `time.hour`
的 12 小时制约定相反 —— 提示词里明确写了这一点。

## 手动新建与每周重复

日历左上角「+」可以不经对话直接建事件。勾选「每周重复」后选星期几、填持续周数，
面板底部实时显示「将创建 N 个事件」。

**重复不存规则，存实例。** 一次展开成 N 行具体事件，理由有三：

1. 排程器、空闲时段、通知计划全部基于具体区间，不用改；
2. 单独删掉某一个周四的课是自然操作，不需要"例外规则"；
3. 用户想改其中一次，改的就是那一行。

批量写入走单个事务（`insertEvents`），半套系列不会留在库里。
展开上限 200 次，防止把「520 周」这种笔误变成灾难。

## 拆解：先问，再拆

目标说得含糊时，硬拆出来的只能是"去研究一下""去制定计划"这类准备工作。
所以提示词允许模型反问——返回 `{"need_clarification": true, "questions": [...]}`
而不是步骤，App 把问题转给用户，最多追问 2 轮，仍不够才退回模板。

```
用户：我想两个月减 15 斤
  ↓
模型：按你给的身高体重，BMI 已在正常范围内；两个月减 15 斤约合每周 1.9 斤，
      高于通常建议的速度。你想要的是改善体脂，还是必须让数字降到某个值？
      （另有 4 个问题）
  ↓  用户回答
模型：11 步，其中「每天走够 8000 步」「每周三次力量训练」
```

## 习惯型步骤

一次性任务和每日习惯是两种东西，`StepRecurrence` 表达后者：

```json
{"kind": "daily"}
{"kind": "weekly", "times_per_week": 3}
```

**模型经常在标题里写"每天"，却不输出对应的字段。** 计划悄悄丢掉频率比没有频率更糟，
所以 `RecurrenceInference` 从标题/描述里确定性推断，validator 在字段缺失时回填：

| 文本 | 结果 |
|---|---|
| 每天… / 每日… | `daily` |
| 每周 3 次… / 每周三次… / 每周两次… | `weekly(3)`、`weekly(2)` |
| 每周复盘一次 | `weekly(1)` |
| 测一次基线 | 无（一次性任务） |

## 时间轴布局

日视图把事件按时间位置和时长画出来，空闲时段就是空白。两处容易静默出错：

1. **裁剪**：昨晚开始、今早结束的事件必须裁到窗口起点，否则整条时间轴被推走。
2. **重叠分列**：两个事件时间交叉时不能叠在一起。`TimelineLayout` 先把事件按
   "传递性重叠" 聚成簇，再贪心分列——同一簇里已结束的列会被后来者复用。

`testFreedColumnIsReusedWithinACluster` 专门覆盖复用：A 10:00–11:00、B 10:30–11:30、
C 11:00–12:00 时，C 应回到 A 那一列，而不是开第三列。

## 通知排期的两个坑

1. **iOS 最多只保留 64 条待触发的本地通知**，超出部分被系统静默丢弃，不报错。
   所以 `NotificationPlanner` 按触发时间排序后只取前 64 条 —— 否则第 65 条看起来
   "已安排"，实际永远不会响。
2. **只对 `confirmed` 事件排提醒**。`proposed` 还只是建议、`done`/`cancelled` 是历史，
   给它们发提醒只会造成噪音。

排期逻辑（`NotificationPlanner`）是纯函数，有 8 个测试覆盖：过去的事件、超出 30 天
视野的、太近而来不及提前 10 分钟的、以及 64 条上限的截断行为。

系统对接部分（`NotificationManager`）只做两件事：请求授权、把计划镜像成
`UNCalendarNotificationTrigger`。用日历组件而不是相对秒数，这样夏令时切换和 App
重启都不会让提醒漂移。

提醒时间是**开始前 5 分钟**，横幅内容是「N 分钟后开始 · 时间区间 · 时长」。

**前台必须显式开横幅**：iOS 默认会吞掉 App 在前台时到达的本地通知。没有
`UNUserNotificationCenterDelegate.willPresent` 返回 `[.banner, .sound]`，用户在
App 里时提醒会静默消失，看起来像"提醒根本没生效"。

> **验证边界**：本沙盒无法授予通知权限（`simctl privacy` 不支持 notifications，
> TCC 写入被拒），因此"授权后提醒真正进入系统"这一步未能实测。已实测的是：
> 从真实数据库算出 2 条提醒（`planned=2`）与权限弹窗正常出现。

## 为什么改时间要走 update 而不是重建

删掉再新建一条事件，新行会丢掉 `step_id` —— 日历上看起来一切正常，但那条事件
不再是某个目标步骤的载体，完成它也不会推进进度。这种断链没有任何报错，只有
若干天后用户发现"我明明做完了，进度怎么没动"。

所以 `updateEvent(id:startAt:endAt:)` 只改两列时间，`step_id` / `goal_id` / `status`
原样保留。测试 `testMovingPreservesStepAndGoalLinkage` 会在移动后立即完成该事件，
断言进度确实推进到 1/4。

改时间时还会查一次冲突：`eventsOverlapping(excluding: 自己的 id)`，界面用橙色提示
"与「xxx」时间重叠"。只提示、不阻止 —— 用户可能就是要重叠（比如线上的会）。
`proposed` 状态的事件不算冲突，它们还只是建议。

## LLM 配置

密钥不进仓库、不进 App 包、不经过 shell 历史。交互式写入一个 gitignored 文件：

```bash
./scripts/setup-llm.sh     # 首次：写入三项配置
./scripts/set-key.sh       # 只换 key，并立刻调接口验证
```

任何 OpenAI 兼容服务商都可以。当前验证过的组合：

| 服务商 | `LLM_BASE_URL` | `LLM_MODEL` |
|---|---|---|
| SiliconFlow | `https://api.siliconflow.cn/v1` | `deepseek-ai/DeepSeek-V4.1-Flash` |
| DeepSeek 官方 | `https://api.deepseek.com` | `deepseek-flash` |

> `base_url` 结尾**不要**带 `/chat/completions`，客户端会自己拼。
> 用错服务商的地址会得到 401，看起来像 key 失效，其实是端点不对。

所有脚本会自动 `source` 它。验证连接：

```bash
./scripts/demo.sh --llm          # 规则 vs 模型 逐句对比
./scripts/demo.sh --llm --raw    # 额外打印模型原始输出，调提示词时用
```

模型广场列表（SiliconFlow）：`GET https://api.siliconflow.cn/v1/models`，带上 `Authorization: Bearer <key>`。

模拟器里跑 App 时，用环境变量透传：

```bash
SIMCTL_CHILD_LLM_BASE_URL="..." \
SIMCTL_CHILD_LLM_API_KEY="..."  \
SIMCTL_CHILD_LLM_MODEL="..."    \
xcrun simctl launch booted com.goalcalendar.app
```

三变量缺任意一个，`LLMConfiguration.load()` 返回 nil，App 自动进入规则模式。

> ⚠️ 正式发布前必须改成走你自己的后端代理。编译进 App 的 key 可以被逆向提取。

## 环境备注

这台机器上 iOS 构建需要两个绕行，脚本里已处理：

- `swift test` 必须加 `--disable-sandbox`：SwiftPM 自带的 sandbox-exec 无法在 DSH 沙盒内嵌套。
- App target 直接编译 `GoalCalendarKit/Sources` 源码，没有走 SwiftPM 依赖 —— Xcode 的包解析器硬性要求写 `~/Library/Caches/org.swift.swiftpm`，该路径被沙盒拒绝。源码只有一份，两边编译的是同一批文件。
- Homebrew 目录权限损坏，所以 XcodeGen 是直接下载的二进制，放在 `.tools/`（已 gitignore）。
- **SwiftUI 宏无法在本沙盒内展开**：`@State`、`@FocusState`、`@Observable`、`#Preview` 会让
  `swift-plugin-server` 报 "malformed response"。因此所有可变状态都放在 `ObservableObject`
  视图模型里（属性包装器不是宏）。新增 UI 时请延续这个写法。
- `./scripts/run.sh` 每次都会重新生成 `.xcodeproj`：XcodeGen 写的是显式文件清单，新增
  `.swift` 文件不重新生成的话 Xcode 根本看不到。
