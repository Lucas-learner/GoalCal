> 目的：7 个人并行开发时，**只有这三个接口不能随便改**。冻结日期：2026-10-23，此后改动需同步本文档。

## 1. 理解层 → 执行层

```python
def parse(
    text: str,
    now: datetime,
    use_llm: bool | None = None,
    context: dict | None = None,
) -> tuple[Action, str]
```

`context` 携带对话状态：`{"expecting": "checkin"}` 时，"一半"/"太累了"/"done"/"没做，太忙了"
这类短回答先按签到语境解析（outcome 进 `checkin_outcome`，原因进 `state`），
明确是新指令（`NEW_COMMAND_INTENTS`）时照常走 LLM/规则流程。

`Action`（`goalcal/llm/action.py`）是唯一允许跨层传递的结构：

```json
{
  "intent": "add_event | move_event | delete_event | query_events | create_goal | delete_goal | schedule_step | schedule_all | refine_steps | log_progress | set_state | chat",
  "title": "meeting",
  "start": "2026-10-22T10:00:00+08:00",
  "end": "2026-10-22T11:00:00+08:00",
  "window": ["2026-10-22T12:00:00+08:00", "2026-10-22T18:00:00+08:00"],
  "duration_min": 60,
  "target": "workout",
  "deadline": "2026-11-20",
  "state": "tired | busy | uninspired | fresh",
  "progress_target": "script",
  "checkin_outcome": "done | partial | none",
  "confidence": 0.9,
  "raw": "原始输入"
}
```

规则：

- 第二返回值是 parser 标识（`llm:parse-v3` / `rules:v1` / `rules:checkin` / `rules:guard` / `goal:clarify`），必须写日志，用于评测归因。
- `schedule_all` 是批量排窗口（“今天下午有空，把任务都排了”）；`refine_steps` 是把下一步拆得更细。
- `window` 是 ISO 时间对（今天下午 / tonight 等时间窗口约束），由 `natdate.extract_window` 从 `when_text`/原文算出，不经 LLM。
- `rules:checkin` 表示签到语境下的短回答解析：`checkin_outcome` 是结果（`none` 即没做），`state` 顺带带出原因（tired→tired、busy→no_time、uninspired→stuck）。
- `delete_goal` 的 `target` 是目标标题；明显“删目标”的句子若被 LLM 误判成 `create_goal`，会用 `rules:guard` 纠正。
- 复杂目标可能先进入澄清态：`Reply.goal_brief` 非空时，下一句走 `agent.continue_goal(...)`，只追问一轮，之后用默认假设生成可调整的计划。
- 过期目标块触发签到态：`Reply.checkin_context` 非空时，下一句走 `agent.continue_checkin(...)`（返回 `None` 表示用户说了新指令，转交 `handle` 并保留上下文）；恢复候选被接受走 `agent.accept_recovery(...)`，写 `RescheduleLog`。

### 1.5 目标计划（LLM）

```python
def generate_plan(
    title: str, deadline: date | None, *, today=None, level="", target="",
    complexity="standard", raw="", tz="Asia/Shanghai",
    instruction="", current_steps: list[str] | None = None,
) -> list[dict] | None
```

- 返回字段：`seq / milestone / title / outcome / est_min / energy / kind`。
- LLM 只返回 JSON；`Plan` schema 校验 4–12 步和字段范围，失败返回 `None`。
- 调用方（`agent.create_goal_from_brief`）拿到计划后写库；`None` 才回退模板。
- 已有目标修改走 `agent.propose_goal_plan(...)`：带 `instruction` 和现有步骤上下文生成**待预览**计划，不写库；用户确认后才 `replace_steps`。
- 步骤可直接用 `goals.update_step(...)` 修改标题、阶段、时长、精力和类型；这是计划管理的主路径，不依赖反复生成。
- 重新拆解会替换步骤并清理旧打卡/目标块；有已完成步骤时 UI 要求二次确认。
- `start` 带时区偏移；`end` 由 `Action.normalized(now)` 补齐。
- 任何解析失败 → 抛给 `parse()` 兜底，**不允许把异常抛到 UI**。

## 2. 排期引擎

```python
def propose(
    req: Requirement,          # est_min, energy(0/1/2), kind, min_chunk
    now: datetime,             # 本地 aware
    busy: list[BusyBlock],     # 本地 aware
    prefs: Preferences | None,
    days: int = 5,
    top_n: int = 3,
    deadline: date | None = None,
    window: tuple[datetime, datetime] | None = None,
) -> list[Candidate]           # 已按分数降序
```

约定：

- 纯函数，**不许查库**。数据由调用方（`agent.py`）查好传进来。
- 给了 `window` 就只在窗口内挖空档打分（窗口可能跨天），窗口外日期不扫描；窗口内没有候选就返回空。
- 返回的候选之间至少相隔 1 小时，避免几个按钮指向同一个空档。
- agent 层实际传 `top_n=6`，UI 按天分组展示。
- 每个候选必须至少有一条 `reasons`，UI 直接展示。
- 新增打分维度只能追加权重常量，不能改函数签名。

## 3. 执行层

```python
def handle(session, user_id, text, now, tz) -> Reply
def accept(session, user_id, step_id, candidate, now, tz) -> str
def accept_batch(session, user_id, batch, now, tz) -> str
def continue_goal(session, user_id, brief, text, now, tz) -> Reply
def continue_checkin(session, user_id, ctx, text, now, tz) -> Reply | None
def accept_recovery(session, user_id, ctx, candidate, now, tz) -> Reply
```

- `handle` 是**唯一**允许写事件的入口（除 seed 外）。
- `accept` 把选定候选写成一个目标块（同一步骤先撤旧块再建新块，重选 = 改期）。
- `accept_batch` 批量接受装箱结果，逐块建 Event（口径同 `accept`），`proposal_accepted` 埋点只记一次。
- `continue_goal` 处理目标澄清的下一句；只追问一轮，之后按默认假设生成可调整的计划。
- `continue_checkin` 处理签到流程里的下一句；返回 `None` 表示用户说了新指令，转交 `handle` 并保留上下文。
- `accept_recovery` 用户选定恢复候选：建新块并写 `RescheduleLog`（旧块保留，供恢复率统计）。
- 所有写操作在调用方的 `session_scope()` 里提交，函数内只 `flush`。
- 失败要返回人话，不抛裸异常。

## 4. 数据约定

| 规则 | 说明 |
|---|---|
| 时间存储 | DB 一律 **UTC naive**；进出用 `timeutil` |
| 计算 | 一律本地 aware（`Asia/Shanghai`） |
| 事件类型 | `external` 用户日程 / `block` 目标执行块 / `buffer` |
| 事件状态 | `planned → done / partial / missed / skipped / moved`，resolve 时写 `resolved_at`；`Event.uid` 是 ICS 导入去重键 |
| 步骤状态 | `todo → done`（`dropped` 为放弃）；`scheduled` 不落库，由"是否存在未来目标块"推导 |
| 步骤增删 | 允许自定义步骤；删步骤同时删打卡、解除事件关联、撤掉目标块 |
| 进度 | 按阶段：已完成阶段数 + 当前阶段完成比例（滚动拆解下总量未知，不按 est_min 加权） |
| 目标拆解 | LLM 生成 3–5 阶段大纲 + 首批 2–3 步（滚动拆解，剩余步骤 <2 自动续批）；失败回退 `planner` 复杂度模板；`Goal.outline` 存阶段大纲 JSON |
| 计划修改 | 步骤可直接编辑；AI 修改先生成预览，用户确认后才替换 |
| 签到 | `Checkin.event_id` 关联被签到的块，`reason` 记原因（tired / no_time / stuck / unwilling） |
| 埋点 | `interactions` 表：每条带 `ts_sim`（模拟时间）与 `ts_wall`（真实墙钟） |
| 完成步骤 | 已到时间的块标 `done` 保留在日历上作完成记录，未来块才取消 |
| 删除 | 事件硬删；目标用 `status=archived` 软删 |
