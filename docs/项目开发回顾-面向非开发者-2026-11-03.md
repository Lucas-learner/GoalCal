# GoalCal 是怎样一步步做出来的

给非开发者的 AI 协作开发回顾 · 整理日期：2026 年 11 月 3 日

> 阅读建议：前半部分按故事阅读，了解一个想法怎样变成可以试用的软件；后半部分用真实故障和协作方法，学习如何判断 AI 到底有没有把事情做好。无需先懂编程。

## 一、先用一分钟认识这个项目

GoalCal 想解决的问题是：我们会把会议放进日历，却很少为长期目标真正留出时间。

例如，你说“我想在一个月内发布第一条短视频”。理想中的 GoalCal 会先弄清目标和期限，给出分阶段计划，让你确认，再为第一步寻找日历空档。如果那天太累、没时间或卡住了，它会帮助调整下一步，而不是让任务一直逾期。

因此，这个项目同时包含三个相互牵连的部分：**理解人说的话、管理目标和步骤、在真实日历中安排时间。** 后来开放给其他人试用，又增加了登录、用户数据隔离和持续运行的要求。

回顾记录可以看到，最费心的地方往往是这些部分之间的连接：系统说“安排好了”，日历里是否真的有记录？用户说“好的”，接受的是刚才哪一个提议？登录成功后，应用是否真的能打开？

## 二、这份回顾依据什么

本报告交叉查看了三类材料：

| 材料 | 能回答什么 | 需要留意什么 |
|---|---|---|
| Codex、Kimi Code 的本地会话 | 用户提出了什么、agent 如何处理、哪里中断或交接 | 会话中的完成汇报需要与代码或验收记录核对 |
| Git 提交历史 | 哪些变化被保存为正式版本、先后顺序如何 | 当前有大量未提交修改，提交历史不能覆盖全部进展 |
| 项目文档、代码、测试及规划实验报告 | 设计理由、具体故障、已有验证和能力边界 | 历史测试数字不代表今天重新测试的结果 |

本次定位到 **26 条 Codex 相关会话索引，其中 8 条为自动审批审查，其余 18 条包含开发、排障、材料整理及本次回顾会话**。Kimi Code 的 GoalCal 目录中找到 **16 份会话状态文件**，另有部分无状态文件的记录目录。并非每条会话都是独立开发任务：有些只是检查命令工具能否连接，有些属于交接或中断后的续接。

OpenCode 本地数据库中未找到以 GoalCal 为工作目录的会话；本次也没有取得早期所有环境中的完整记录。因此，**10 月 21—22 日的原型阶段主要根据提交历史重建，10 月 23 日以后的过程有更多会话支持**。不能据此认定所有工作都由已找到的 agent 完成，也不能比较不同模型的整体能力高低。

以下以北京时间组织日期。原始会话中的密码、邀请码、用户身份和日历正文不收录。此次为历史研究与文档整理，没有重跑应用测试，也没有验证当前线上服务。

## 三、从想法到试用：六个阶段

### 第一阶段：先让核心流程跑起来（10 月 21—22 日）

10 月 21 日，仓库出现首个原型提交 `0cf5545`：规则解析器、排期器、Streamlit 界面和评测脚本。可以把它理解为先搭出一家店的基本柜台：能接单、处理、返回结果。

“规则解析器”是按预设表达理解指令的程序。例如，“明天十点开会”可以被转换成新建日程的操作。“排期器”负责从空档中选择合适时间。Streamlit 则帮助用 Python 快速搭建网页界面。

10 月 22 日，项目把关注点逐步扩展到目标推进：目标拆解、进度回报、过期任务签到、不同原因下的恢复动作，以及滚动规划。滚动规划的意思是先给整体方向，只详细安排眼前几步，再依据完成情况补充后续步骤。

其中一个有辨识度的产品选择是：没完成任务时先问原因。太累可以降低行动负担，没时间可以改成短启动块，卡住了可以拆成更具体的动作。这使产品从“记事日历”向“帮助重新开始的工具”发展。

**这一阶段的启发：**先验证“说出目标 → 得到下一步 → 找到时间 → 回报结果”的闭环，再逐步增加能力。功能之间能接起来，比单个按钮数量更有意义。

### 第二阶段：从自己的原型变成别人能用的服务（10 月 23 日）

用户提出了一个范围明显扩大的要求：把这台主机当服务器，让不同用户从互联网访问。

这句话带来的工作远超“生成一个网址”：需要注册和登录，需要确保甲看不到乙的数据，需要限制共享 AI 额度，需要保留旧数据，需要让程序异常退出后能恢复，还需要备份和维护说明。

Codex 会话中先形成了面向约 5—20 人邀请试用的实施方案，随后由另一会话接续落地。最初计划使用 Cloudflare Tunnel，后续试用文档和执行记录显示实际入口采用 ngrok。**这是方案与实际落地发生变化的例子，回顾时必须分别看。**

可以把最终服务路径想象成：

```text
用户浏览器 → 公网 HTTPS 入口 → 本机登录网关 → GoalCal 应用 → 数据库
```

登录网关是在后续解决刷新登录问题时加入的，不能把这整条最终路径当成 10 月 23 日一次完成的结果。

这一阶段也加入日志与反馈入口。日志帮助定位“什么时候、哪个环节失败”，反馈入口帮助用户描述“我本来想做什么”。两者需要配合使用。

**这一阶段的启发：**自己能演示与别人能稳定使用，验收标准不同。一旦涉及多个人，账号、权限、数据和维护就是产品本身的一部分。

### 第三阶段：让用户看得懂，也能反悔（10 月 25—26 日）

随着能力增加，三栏界面和大量操作按钮开始显得拥挤。开发方向转为以 Chat 为入口，把 Goals、Calendar 和 Settings 分成独立页面。

重要变化包括：

- 新目标先展示草稿，确认后才保存；可以修改、取消，或只保存而不排期。
- 候选时间默认展示少量选项，可以回复“第二个”或重新指定时间范围。
- 常用操作保留在外层，编辑、删除等操作收进 More；整个目标的管理放进 Manage goal。
- 用统一的暖色、字体和间距规则约束页面，减少 agent 每次自行发挥造成的不一致。

这轮还有一个不易从截图看出的改进：同一份草稿重复确认时，不能重复创建目标。网页可能重试，用户也可能多点一次，因此系统需要识别“这是同一次请求”。开发中称为“幂等”，日常可以理解为：**同一张订单重复提交，不应重复下单。**

Kimi 的前端与交互主会话、Codex 的小范围 UI 子任务及后续接续会话都参与了这一过程。一条子任务明确只允许修改 `goalcal/ui/progress.py`，保留原来的业务行为与回调。这是将并行工作限制在可控范围内的实例。

**这一阶段的启发：**可用性既包括界面是否清楚，也包括误点、重复点击和取消操作时，系统能否保持一致。

### 第四阶段：让对话真正接得上（10 月 26—27 日）

早期方案主要由手写规则决定流程，模型负责部分理解或措辞。它能处理很多明确指令，却在连续对话里暴露出问题：系统自己提议“要不要安排”，用户回答“好”，它却接不住；用户换了话题，旧流程仍在等待；模型失败后，回复变成不了解上下文的模板。

项目随后重做对话层：由模型结合当前状态理解这一轮话语，输出结构化决定，再交给程序验证和执行。

可以把分工理解为：

```text
用户的话 → AI 理解“想做什么” → 程序检查“能否这样做”
         → 执行实际操作 → 根据执行结果回复
```

这里保留了三条重要边界：模型不能直接改数据库；日期运算主要由专门程序处理；本地显示时间与数据库统一存储时间在明确边界转换。

同时，系统开始记录“当前谈的是什么”和“刚才提出了什么”。例如，助手建议为网球安排时间，用户说“可以”时，应当接受绑定到网球目标的提议，而不是随意选择另一个活跃目标。

会话中有真实的网球与半马串线案例：用户修改网球期限，系统只在文字上说改好了；随后接受重新规划提议，却触发了半马细化。修复方向包括把提议绑定到具体目标和步骤，执行前再检查，期限修改必须真正保存。

这说明，对话能力既需要语言理解，也需要可靠的业务指向。“听起来合理”与“做对了事”必须同时验证。

### 第五阶段：开始追问 AI 生成的计划有没有价值（10 月 28 日）

后续发现，滚动规划虽然不断产出新步骤，却可能一直停留在准备和低强度练习，迟迟不接近最终目标。

Kimi 的“修复游泳训练执行问题”会话及 `bench/prompt_eval/` 报告记录了对照实验：用半马、游泳、备考、视频、吉他等情境，模拟完成一批任务后，再让模型生成下一批。

改进围绕几个问题展开：剩下多少天？还有哪些阶段没开展？最近是否一直停在同一阶段？重复练习这一次具体增加了什么？任务太轻时是否也应该适当增加，而不是只会减量？

实验又发现，过分强调按期进入收尾，可能让半马计划还没达到阶段距离，就提前减量。后续规则要求明确的阶段峰值目标先达成，再进入收尾。在记录的修正版模拟中，30 天情境先生成达到 14 公里阶段目标的步骤，再进入减量阶段。

**这些是生成计划的模拟结果，不是用户实际完成训练的结果，也不构成运动训练建议。** 它们能够支持“这轮输出是否更符合设计约束”，不能证明真实目标达成率。

**这一阶段的启发：**AI 返回了合法格式，只说明系统能读取它。评价内容还要看有没有推进、有没有尊重期限，以及是否遗漏关键目标。

### 第六阶段：打磨细节，整理可解释的证据（10 月 29—31 日）

后续工作越来越具体：在 Calendar 标题旁添加导入入口，让新用户发现设置里的导入功能；调整聊天左右布局、气泡和按钮颜色；支持按次数或不限次数使用邀请码。

颜色修改中也发生过一次理解偏差：用户希望其他元素跟随既有按钮颜色，agent 却改了作为参照的按钮。用户纠正后再恢复。这类返工说明，视觉需求最好明确“以哪个现有元素为基准、要改哪些元素”，最后检查页面实际呈现。

语音输入则停留在方案讨论：讨论了录音后转写、准确率、等待时间和并发测试，用户倾向先做独立实验，再决定是否接入。不能把这段讨论列为已经上线的语音功能。

10 月 31 日还整理了课程中期报告与附录。相关会话对测试数字的解释很有价值：网页自动化测试、规则解析评测、规划模拟和 iOS 测试属于不同证据，不能拼成一个“AI 准确率”。本报告聚焦当前网页项目，未独立审阅 iOS 开发过程。

## 四、三个真实案例：学习如何判断软件是否做好

### 案例 1：服务显示正常，用户却进不去

**用户看到的现象：**刷新后需要重新登录，公网表单提交失败，或登录后长时间停在加载状态。

**为什么容易误判：**健康检查返回 200，只说明服务响应了请求。它不保证登录表单能提交，也不保证登录后网页与应用持续通信的连接正常。

验收记录展示了逐层排查：

| 检查层次 | 记录中的问题 | 修复或验证方向 |
|---|---|---|
| 登录状态 | 硬刷新后丢失登录 | 由同源网关管理浏览器会话 Cookie |
| 表单提交 | 公网 HTTPS 与内部协议不同，导致误拒合法请求 | 使用表单令牌校验，并在公网浏览器实际提交 |
| 登录后的应用连接 | WebSocket 来源与内部地址不一致，内部应用拒绝连接 | 网关校验公网来源，再按内部服务要求转发 |
| 退出 | 页面令牌过期，退出失败但会话仍有效 | 撤销登录会话、清 Cookie、跳回登录页 |

10 月 28 日又报告了过期后出现“看起来能登录却不能用”的页面。Codex 当时因命令环境超时未能修改；后续 Kimi 接续处理登录界面，当前代码也区分了网关会话过期页面与本机直连登录表单。对这类跨会话事项，应分别保留“最初未完成”和“后续已有实现”的证据。

**可学的方法：**验收写成“打开公网地址 → 登录 → 看到聊天输入框 → 刷新 → 仍可用 → 退出 → 必须重新登录”，比“服务返回正常”更接近用户需要。

### 案例 2：新数据库测试全绿，旧数据却报错

**用户看到的现象：**已有账号的数据打开报错，提示 `steps.draft_id` 字段不存在。

**原因：**草稿标识误加到了 Step 数据模型，但旧库迁移只给 Goal 加了字段。测试直接按最新模型新建数据库，所以没有暴露旧表与新程序之间的不一致。

**处理：**移除 Step 上误加的字段，保留 Goal 的防重复机制；加入真实旧版表结构的迁移测试，并在生产数据库的隔离副本中验证业务流程。

可以把“数据库迁移”理解为给正在营业的档案室换目录：新档案室整齐，不代表旧档案搬过来仍然能查到。

**可学的方法：**有历史用户的软件，既要测试“从零开始”，也要测试“带着旧数据升级”。保护已有数据也是完成标准。

### 案例 3：测试都通过了，独立审查仍发现对话死循环

Kimi 第二阶段交互实现记录曾报告 563 项测试通过。随后独立审查发现：签到恢复阶段用户说“算了”，系统只关闭提议，没有推进或退出签到，后续可能反复回复而无法脱离流程。

测试覆盖了普通草稿场景下的拒绝，却没覆盖签到恢复场景中完整的模型路由路径。类似问题还包括闲聊提议无法被接受、含糊回答被误当作修改草稿等。

随后子任务遇到额度限制，中断时仍有待办。Codex 接续会话和后续文档记录了继续修复、扩大验收的过程。不能将中断前的“实现完成”直接当作全部任务完成。

**可学的方法：**测试通过说明已检查的情境满足断言。再找一个不同视角，按真实多轮对话走一遍，仍可能发现遗漏。一次审查的价值可以大于继续增加很多相似测试。

## 五、不同 agent 是怎样协作的

这些会话显示的是一条多次续接的工作链，而不是一个 agent 从头到尾连续完成全部开发。

| 参与者或角色 | 记录中可确认的工作 | 对非开发者的启示 |
|---|---|---|
| 用户 | 确定方向、提出体验反馈、纠正视觉理解、决定先实验还是接入 | 人负责定义什么才算有用，并持续检验 |
| Codex 开发会话 | 公网多用户方案及实施、Kimi 中断后的接续、登录和交互修复、后期 UI 与报告整理 | 换 agent 后要先重建事实，再继续工作 |
| Kimi Code 主会话及子任务 | UI 与主题重构、对话重设计、独立审查、滚动规划实验、登录页及邀请码改进 | 实现、审查、实验适合形成不同任务 |
| 小范围开发子任务 | 在指定文件和边界内调整 UI，保留外部行为 | 并行工作先约定“谁改哪里” |
| 自动审批审查 | 判断部分工具操作是否可执行 | 这属于操作审批，不能当作功能测试或代码质量审查 |

这些是本项目观察到的分工，不是对不同模型的普遍排名。会话有缺失，执行环境、任务规模和上下文也不同。

交接中反复出现的有效做法，是先检查当前文件与未提交修改，再阅读必要的历史记录，确认上一轮停在哪一步。旧会话里的命令只是历史材料，不能重新照做；例如过去生成邀请码或重启服务，不意味着回顾时应该再次执行。

10 月 28 日的工具连接故障也值得记录：连续几个“能否访问代码”“请执行 pwd”的会话并没有带来产品进展。后续记录显示，特定版本在 Orca 中出现握手超时，回退版本后恢复。这里能支持的是当时环境下的排查结论，不能扩大为某版本在所有环境中都有问题。

**好的交接至少包含：目标、当前状态、已修改内容、验证结果、未完成事项、不能覆盖的现有工作。** 尤其当前仓库存在大量未提交修改，接手者只看最后一次 Git 提交，会遗漏之后的开发成果。

## 六、怎样读懂测试数字

记录中的通过数随开发增长，例如 10 月 25—26 日的历史验收从 422 项发展到 437 项，对话后续会话记录到 602 项，10 月 28 日规划修改记录 643 项，10 月 31 日记录 647 项。这些反映不同时间、不同测试集合的历史快照，不是本次新跑出的结果。

| 证据 | 能说明什么 | 不能单独说明什么 |
|---|---|---|
| 自动化测试通过 | 被覆盖的程序行为符合预设要求 | 所有用户路径都没有问题 |
| 规则解析 88/88 | 通过这 88 个既有评测案例 | 现实自然语言理解准确率为 100% |
| 浏览器验收 | 当时、该环境、该操作路径能走通 | 所有浏览器、网络、用户都可用 |
| 规划模拟 | 模拟条件下生成内容的递进和约束表现 | 用户真实完成目标的概率 |
| 用户试用指标 | 实际使用中的接受、恢复和推进情况 | 未收集的数据所对应的效果 |

尤其应注意，课程材料会话已指出：规则评测包含指导修复的案例，并允许 90 分钟的开始时间容差，不属于独立保留测试集。规划实验假设生成步骤得到完成，也不能替代真实用户长期试用。

对于非开发者，判断汇报时可以问三句：**测了什么情境？看到了什么实际结果？还有什么没有验证？**

## 七、如果你也想用 AI 开发，可以照着怎样做

下面的方法来自本项目中的成功做法与返工经验。

1. **先描述用户要完成的事。** 例如：“新用户说出目标后能预览、修改，再确认保存。”这比只要求增加 AI 功能更明确。
2. **让 agent 查清现状。** 找到相关代码、旧数据要求和未提交修改，避免在错误版本上开始。
3. **把大需求分成可验收的小步。** 登录、用户隔离、草稿确认、候选选择分别做清楚，每一步都有完成条件。
4. **把 AI 理解和实际执行分开。** 模型提出动作，由程序核对对象、权限、时间和确认状态，再保存结果。
5. **用具体操作反馈问题。** “今晚想跑步 → 可以 → 第二个，但日历没有记录”比“AI 不聪明”更容易定位。
6. **检查数据和完整流程。** 回复称已修改，就核对保存结果；页面能打开，就继续验证登录后、刷新后和退出后。
7. **新增能力前先验证不确定性。** 像语音输入和规划质量一样，可以先用独立实验判断准确率、速度或内容质量。
8. **结束时留下交接记录。** 写清哪些完成、哪些只是方案、哪些失败、哪些还要真实用户复试。

可以复用下面这段任务说明：

> 我希望用户在【情境】下能够【完成动作】。目前问题是【可复现现象】。请先检查当前实现和未提交修改，再完成必要改动。完成标准是【具体操作与可观察结果】。请说明验证证据和未完成部分，并保留已有用户数据。
