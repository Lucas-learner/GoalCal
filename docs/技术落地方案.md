## 0. 一句话

不做“能聊天的日历”，做**掉线之后还能把目标接回来**的日历。
F1–F4 四个功能不变，但主线从“拆解”换成“**中断恢复**”，这是差异化和 demo 的记忆点。

核心指标（比课程 6 项更能讲故事）：

- **推进率** = 完成的目标时间 / 可用空闲时间
- **72h 恢复率** = 错过一次后三天内重新排上的比例
- **建议接受率** = 接受的候选 / 展示的候选

## 2. 三层架构

```
对话层  Streamlit chat
        ↓ 说人话
理解层  llm/parser.py  (LLM → Action JSON，规则兜底)
        ↓ 只传结构化意图
决策层  domain/scheduler.py  (确定性打分，无 LLM)
        ↓ 候选 + 理由
执行层  agent.py → domain/calendar_service.py → DB
        ↓
展示层  周视图日历 / 进度卡 / 候选卡片
```

为什么这么分：

- 评测能干净地做消融（“单 prompt vs pipeline”）
- 换模型 / 换日历组件不动业务逻辑
- 7 个人并行开发时，接口不变就不会互相踩

接口定义见 `docs/接口契约.md`。

## 3. 排期引擎

```
score = 0.5
      + 精力匹配      (任务需要 2，槽位只有 0 → -0.36)
      + 时段偏好      (+0.10)
      + 任务类型匹配  (deep 放上午 / admin 放下午)
      − 拖延成本      (每往后一天 -0.035)
      + 截止压力      (≤7 天 +0.10)
      − 当日过载      (超过 120 分钟 -0.45)
      − 切换成本      (紧接会议 -0.07)
      − 午饭保护      (-0.12)
```

- 15 分钟网格，空档两侧各留 10 分钟缓冲，<20 分钟的碎片直接丢弃
- 每天目标工作上限 120 分钟，避免“推荐得很积极，用户做不完”
- 输出 3 个候选，每个候选必须带一条人话理由（评审很吃这个）

单测覆盖：不重叠、不过去、深任务在上午、碎片跳过、过量惩罚。

M1 用模板库（video / learn / sideproject / fitness / generic），每个 10 个叶子任务，
带 `est_min / energy / kind / milestone`。

- bge-m3 向量化，检索 top-3 注入 prompt
- **消融**：有 RAG vs 无 RAG 的拆解可用性评分 —— 这是报告里 RAG 那一节的证据

固定 10% 的做法已放弃：改成“叶子任务 ≤45 分钟”，进度按预估时长加权。

## 5. 中断恢复（12 月的主线）

错过一个 block 后，不问“你为什么没做”，只给四个按钮：

| 原因 | 系统动作 |
|---|---|
| 太累 | 换一个 `energy<=1` 的步骤，或把当前步骤拆成 2 次 |
| 没时间 | 缩到 15 分钟，只做“打开文件” |
| 卡住了 | 换一个依赖更少的步骤，并给一个 5 分钟启动动作 |
| 不想做了 | 重谈截止日 / 归档目标（不羞辱用户） |

所有动作写 `reschedule_logs`，用于算 72h 恢复率。
